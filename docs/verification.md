## 服务重启与返工

第一次真实任务创建一个指定两行内容的文件。独立检查精确内容后记录接受。随后重启网关服务，并对同一个任务发起返工，只修改指定的一行。

返工完成后再次独立核验文件内容与 Thread 一致性，任务保留原 ID、工作区和历史，执行轮次增加，结果再次被接受。

重启发生在已完成任务和后续返工之间。这证明任务/会话绑定能跨服务重启使用，不能扩大解释为所有运行中断都能无损自动续跑。

## 豆包工作端到端

通过正常应用界面观察到以下链路：

1. 豆包读取 `Doubao Codex Executor` Skill。
2. 发现连接器工具，调用 `codex_health` 和 `codex_workspaces`。
3. 调用 `codex_submit`，保存任务 ID，再调用 `codex_wait`。
4. Codex 在测试工作区创建要求的文件。
5. 豆包独立读取文件，检查字节数、行数及内容，随后调用 `codex_accept`。
6. 豆包对话显示最终结果；网关持久状态也为 `completed + accepted`。

测试文件内容为 `Doubao delegated this task to Codex.` 加一个末尾换行，共 37 字节。另用 Node `assert.equal` 独立比较了完整文件内容。验证依据是实际工具调用、文件和持久状态，不仅是模型的文字陈述。

## 过程中暴露的问题

- 新建 Codex Thread 在第一轮之前可能没有 rollout，立即 `thread/resume` 会失败。实现已区分当前进程中的新空会话与可恢复的已有会话。
- 模型目录或全局默认名称不代表当前认证方式支持推理。真实调用曾被模型权限拒绝，随后在网关专属配置选择实际可用模型完成验证；没有自动 fallback 或更改全局 Codex 默认配置。
- 直接以 Desktop 下的源码目录启动后台服务时出现过启动配置错误，因此正式安装复制运行代码到 Application Support。

这些失败保留在开发任务历史中，没有通过删除记录掩盖。具体私人标识和产物不随公开文档发布。

## 未覆盖范围

未验证或承诺其他操作系统、Codex 桌面侧栏自动同步、关机持续执行、已结束豆包对话的自动唤醒/主动通知、网页自动托管、文件自动上传或多租户隔离。
